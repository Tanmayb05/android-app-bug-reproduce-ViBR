Background

What is ViBR?

ViBR is an automated pipeline. Input: a video of a bug being reproduced. Output: the bug replayed on a real device via ADB.

  • Segment the video into actions.
  • Compare recorded GUI state vs live device.
  • Replay actions on device.

What I tested

ViBR was evaluated on screen recordings. I gave it handheld videos.

  • Input = handheld capture: a phone filming another phone's screen while a human reproduces a bug.
  • ViBR's paper datasets, Themis, GIFdroid, V2S, are 100% screen recordings.
  • 19 apps, Gemini-2.5-pro as the VLM, real emulator replay.
  • Each run self-labeled a failure category; I re-traced every run to its true origin.

Same UI content. Fundamentally different pixel distribution.

Method

Find the earliest wrong output, not the loudest late failure

A failure often becomes visible late, such as at 2.7 State Consistency, but was caused earlier. I traced logs backward to the earliest stage whose output was already wrong.

Main cause #1 · Scene Detection

What breaks: 9 of 19 apps

General cause: CLIP answers "how similar is this whole frame to the last frame" when segmentation needs to answer "did a discrete user action occur."

Scene Detection · rapid low-pixel changes

Six real taps can look like one continuous scene

Each calculator tap changes only a few pixels. The unchanged background and layout dominate the CLIP embedding, so consecutive tap frames stay above the 0.95 threshold.

The failure is not a camera artifact. A screen recording of rapid 3, +, 6 creates the same whole-frame similarity problem.

Scene Detection · verdict

Mostly engineering fix, not the new paper

  • Sub-second tap sequences produce the same CLIP curve whether screen-recorded or handheld.
  • Handheld may add frame-rate jitter, autofocus, and blur, but those are compounding factors, not the driver.
  • Fix family: lower or adaptive thresholds, motion-vector signals, higher sampling in rapid-interaction windows.

Verdict: important, frequent, but capture-independent.

Main cause #2 · Region Detection

What breaks: DINO is starved by the keyframe

GroundingDINO is not necessarily malfunctioning. It is operating on a keyframe where the UI is occluded, degraded, or too low-salience to propose the target.

Region Detection · why it happens

Handheld capture creates a failure screen recordings cannot contain

Finger occlusion is structurally impossible in a screen recording. There is no finger between camera and screen when the screen is the recording source.

Handheld capture also injects glare, off-axis perspective, hand-tremor motion blur, variable lighting, autofocus artifacts, and phone-codec artifacts.

A human can see the finger and see the missing box. ViBR's dataset cannot surface that problem.

Region Detection · verdict

This is the genuine research gap

ViBR's Phase 2 was designed and evaluated on clean, occlusion-free, artifact-free screen recordings. Its datasets exclude camera-captured video by construction, and its threats-to-validity section does not consider imaging artifacts layered on UI content.

Pre-process

Dehaze, deblur, deglare, or de-occlude frames before region detection.

Adapt detector

Fine-tune region detection on camera-captured UI imagery.

Aggregate frames

Vote across adjacent frames so transient occlusion does not kill the step.

ViBR can't surface this problem because its dataset excludes it. That's exactly why it is a paper.

From root cause to design decision

Cause #2 is fatal because ViBR has one frame and no memory

ViBR's failure mode

Region Detection runs per step on one live frame. Finger, glare, or distortion in that single frame is fatal.

src_llm's opening

Stage 1 builds memory from multiple keyframes sampled across the whole video.

Scope boundary

This enables robust multi-frame selection; it does not automatically solve every bad keyframe today.

Cause #2 is fatal because ViBR has one frame and no memory. src_llm is built around many frames and a memory.

From gap to proposal

src_llm: analyze once, automate from memory

ViBR re-detects per step against a live frame that may carry occlusion, glare, or codec artifacts.

I propose src_llm: a two-stage architecture that analyzes the video once to build reusable task memory, then uses that memory to drive on-device automation.

Architecture

Two stages, one memory

Stage 1 · offline, once per video

Extract frames, select keyframes, drop near-duplicates, ask the VLM to analyze the keyframe set, and write structured memory.md.

Stage 2 · online, per automation step

Load memory, screenshot the device, decide the next action, execute tap/type/scroll/wait, log, and repeat until done.

Why this addresses the handheld-video gap

The architecture creates the aggregation point ViBR lacks

Memory from the whole video

Keyframes are selected across the recording, not derived fresh from one fragile live frame.

Bad frame is no longer automatically fatal

An occluded frame must survive filtering and beat adjacent cleaner frames to poison the memory.

Honest scope

The robustness mechanism is the follow-on contribution: multi-frame voting before memory is committed.

This is a better substrate for an occlusion/artifact fix, not a claim that memory alone magically solves occlusion.
